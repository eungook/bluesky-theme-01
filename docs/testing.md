# 테스트

## 목적

**블루스카이가 내부 구조를 바꿔서 우리 확장이 정상 동작하지 않게 되는 것을 사용자보다 먼저 알아채는 것**이 테스트의 최우선 목적이다. 우리 확장은 블루스카이의 인라인 `style` 값에 CSS 선택자를 거는 방식이라, 블루스카이가 값이나 방식을 바꾸면 오류 없이 조용히 안 먹는다. 그래서 실제 사이트를 열어 그 가정이 아직 맞는지 확인한다.

테스트는 세 종류다. 모두 `bun run test:live`로 돈다.

1. [hover 색 확인](#1-hover-색-확인-라이트-다크) (로그인 없음)
2. [설정 주소 확인](#2-설정-주소-확인-로그인-필요) (로그인 필요)
3. [색상 테마 섹션 주입 확인](#3-색상-테마-섹션-주입-확인-로그인-필요-확장-올림) (로그인 필요, 확장을 올림)

## 1. hover 색 확인 (라이트, 다크)

[tests/live/hover-background.test.ts](../tests/live/hover-background.test.ts)

- **대상:** `https://bsky.app/profile/bsky.app` (로그인 없이 열리는 공개 화면)
- **조건:** 같은 확인을 두 모드에서 한다. 확장은 올리지 않는다.
  - **라이트:** `colorScheme: 'light'`. `<html>`에 `theme--light`가 붙는다.
  - **다크:** `colorScheme: 'dark'`. 블루스카이는 기본이 "시스템" 모드라서 브라우저의 `prefers-color-scheme`을 따라 `theme--dim`이 붙는다. (`theme--dark`는 계정 설정으로만 고르는 것으로 보여 이 방법으로는 열리지 않는다.) `colorScheme`은 Playwright가 브라우저에 주는 옵션이고 테스트 러너의 설정이 아니다. 옵션을 안 줘도 라이트가 기본이지만 명시한다.
- **확인하는 것:** 각 프로필 탭(`role="tab"`)에 마우스를 올렸을 때, 블루스카이가 인라인 `style`에 넣는 `background-color`가 [theme.css](../src/content/theme.css)의 hover 치환 규칙이 키로 쓰는 값인가. 라이트는 `rgb(249, 250, 251)`, 다크(어둑함)는 `rgb(28, 39, 54)`이다. 테스트는 theme.css가 같은 키를 쓰고 있는지도 먼저 본다.
- **하지 않는 것:** 확장이 실제로 색을 바꾸는지, `theme--dark`(어두움), 설정 화면, 왼쪽 메뉴, 인라인 색 전체 수집.
- **실제로 확인한 모습:** 로그아웃 상태의 이 화면에는 탭이 다섯 개(Posts, Media, Videos, Feeds, Starter Packs) 있고 두 모드 모두 전부 기대한 색이 된다. 기대값을 일부러 틀리게 해서 실패하는 것(실패 메시지에 탭 이름과 실제 값이 나오는 것)도 두 모드에서 확인했다.

### 실행

```bash
bunx playwright install chromium   # 처음 한 번
bun run test:live
```

실제 사이트를 여는 테스트라서 네트워크가 필요하고 8초 안팎 걸린다. Playwright는 러너가 아니라 라이브러리로만 쓰고, 러너는 `bun test`다.

### 실패했을 때

- **"접속하지 못했다":** 네트워크 문제일 수 있다. 다시 해 본다.
- **"role=tab 요소를 찾지 못했다":** 블루스카이의 프로필 화면 구조가 바뀌었다. 우리 확장의 다른 가정도 의심한다.
- **"라이트 모드로 열리지 않았다":** `<html>`의 `theme--light` 방식이 바뀌었다. 확장의 `themeBaseOf`도 영향을 받는다.
- **"인라인 background-color가 … 이 아닌 탭이 있다":** 블루스카이가 hover 색을 바꿨거나 인라인이 아닌 방식으로 옮겼다. theme.css의 치환 규칙을 고쳐야 한다. 새 값은 실패 메시지에 나온다.

실제 사이트가 대상이라 **우리 코드가 아닌 이유로도 실패할 수 있다.** 배포 직전의 합격/불합격 기준이 아니라 "블루스카이가 바뀐 것 같다"는 경보로 읽는다.

## 2. 설정 주소 확인 (로그인 필요)

[tests/live/settings-path.test.ts](../tests/live/settings-path.test.ts)

- **왜:** 블루스카이가 설정 > 모양의 주소(`/settings/appearance`)를 바꾸면 우리 확장의 선택 화면이 안 뜨고, 도구 모음 아이콘은 없는 주소를 연다. 이 주소는 [selectors.ts](../src/content/selectors.ts)의 `APPEARANCE_PATH`와 [background](../src/background/index.ts)에 있다.
- **확인하는 것:** 로그인한 상태에서 `https://bsky.app/settings/appearance`를 열었을 때 **다른 주소로 넘어가지 않고 오류 없이 그대로 열리는가.** 서버의 HTTP 리다이렉트, JS가 뒤늦게 바꾸는 주소(4초 기다린다), 4xx/5xx 응답을 모두 본다. 테스트는 background가 같은 주소를 쓰고 있는지도 먼저 본다.
- **하지 않는 것:** 확장을 올리지 않는다. 화면 안의 내용(색상 모드 섹션의 구조 등)도 보지 않는다. 그래서 **같은 주소에 "페이지 없음" 화면이 뜨는 경우는 못 잡는다.** (이 앱은 SPA라서 없는 경로도 같은 주소에서 화면만 바뀔 수 있다. 그 확인은 later에 있다.)
- **확인한 것:** 로그인과 세션 재사용 둘 다 통과한다(7~9초). 접근 판정(`accessProblems`)은 로컬 서버로 만든 정상, HTTP 리다이렉트, JS 리다이렉트, 주소 바꿔치기, 404 다섯 경우를 각각 맞게 구분했다. 실제 사이트에서 실패하는 모습은 만들 수 없어서 보지 못했다.

### 로그인과 비밀

- 계정 정보는 `.env`의 `BLUESKY_USERNAME`, `BLUESKY_PASSWORD`에서만 읽는다(Bun이 자동으로 읽는다). `.env`는 `.gitignore`에 있다. 값은 출력하지 않고, 실패 메시지에도 가려서 낸다.
- 로그인은 처음 한 번만 하고 세션을 `.auth/bluesky.json`에 저장해 다시 쓴다. 이 파일에는 토큰이 들어 있어서 `.gitignore`에 있고 권한은 본인만 읽게(0600) 둔다. 만료되면 지우고 다시 로그인한다. 지우려면 `.auth/`를 삭제한다.
- **전용 계정이나 앱 비밀번호 사용을 권한다.** 이 테스트는 계정으로 로그인만 하고 아무것도 바꾸지 않는다. 앱 비밀번호로 웹 로그인이 되는지는 확인하지 못했다. 2단계 인증(이메일 코드)이 켜져 있으면 자동 로그인이 막힌다.
- 로그인이 실패하면 "로그인에 실패했다…"로 알린다. 이때는 블루스카이가 바뀐 것이 아니라 계정 문제일 수 있다.

### 실패했을 때

- **"…이 정상적으로 열리지 않는다":** 이유가 줄마다 나온다. 다른 주소로 이동했다면 블루스카이가 설정 주소를 바꿨을 가능성이 크다. `APPEARANCE_PATH`와 background의 주소를 고친다.
- **"로그인에 실패했다":** `.env`, 2단계 인증, 요청 제한을 확인한다.
- **".env에 BLUESKY_USERNAME과 …":** `.env`에 두 값이 없다. 이 테스트는 건너뛰지 않고 실패한다. 경보가 조용히 꺼지는 것을 피하기 위해서다.

## 3. 색상 테마 섹션 주입 확인 (로그인 필요, 확장을 올림)

[tests/live/injection.test.ts](../tests/live/injection.test.ts)

- **왜:** 블루스카이가 설정 화면의 구조를 바꾸면 우리 확장은 색상 모드 섹션을 못 찾고 **오류 없이 아무것도 안 넣는다.** 사용자는 선택 화면이 없다는 것만 알게 된다.
- **확인하는 것:** 확장의 빌드(`dist/`, 테스트가 시작할 때 `bun run build`로 새로 만든다)를 Playwright의 Chromium에 올리고 로그인한 `/settings/appearance`를 열었을 때, ① `[data-bt-theme-section]`이 나타나고, ② 하나만 있고, ③ 색상 모드 섹션 바로 뒤에 있고, ④ 테마 선택지가 `THEMES` 개수만큼 그려졌는가. 라이트 모드(`colorScheme: 'light'`)로 본다.
- **확장 코드는 바꾸지 않고 결과만 본다.** selector 로직을 테스트에 복사하지 않으므로 "테스트의 정답"과 "실제 코드"가 어긋날 수 없다.
- **결정(2026-10-14): `index.ts`의 selector 로직을 따로 모듈로 뽑지 않는다.** 위 방식이면 필요하지 않기 때문이다. 그 대가로, 고정된 화면에 변형을 가하는 단위 테스트가 필요한 시나리오(예: 블루스카이가 색상 모드 뒤에 radiogroup 하나짜리 새 설정을 넣으면 우리가 그것을 어두운 테마 선택으로 착각해 숨기는 경우)는 지금 테스트할 수 없다. 필요해지면 그때 `index.ts`에서 두 검색 함수(색상 모드 섹션, 어두운 테마 선택)를 부작용 없는 모듈로 옮긴다. `index.ts`는 import하는 순간 `observer`와 `chrome.storage` 호출이 실행되어 테스트에서 import할 수 없다.
- **확장을 올리려면 Playwright의 Chromium이 필요하다.** 정식 Chrome은 확장을 옆에서 불러오는 옵션을 없앴다(Playwright 문서). 이 테스트는 파일(`storageState`)이 아니라 프로필 폴더(`.auth/chromium-profile`)에 세션을 남긴다. 둘 다 `.gitignore`의 `.auth`에 있다.
- **확인한 것:** 정상 실행에서 통과한다(프로필이 있으면 2~3초, 로그인과 빌드가 필요한 처음은 10초 안팎). 실패하는 두 경우도 실제 화면에서 확인했다.
  - 확장을 안 올리면: "콘텐츠 스크립트가 이 페이지에서 실행되지 않았다"로 구분해서 알린다(`contentScriptRan: false`).
  - 블루스카이가 `role="radiogroup"`을 바꾼 상황을 흉내 내면(우리 섹션은 건드리지 않음): 섹션이 0개라고 알리면서 "화면에서 role=radiogroup을 찾지 못했다. 구조를 바꿨을 가능성이 크다"를 함께 낸다. 세 번 반복해 같은 결과였다.
- **실패했을 때 읽는 법:** 실패 메시지의 마지막 줄에 화면 상태 요약이 JSON으로 나온다(주소, `<html>` 클래스, 확장 실행 여부, radiogroup 개수, 첫 radiogroup의 선택지 수와 부모의 부모 유무). 그것으로 "확장이 안 돌았다", "주소가 바뀌었다", "테마 클래스가 바뀌었다", "radiogroup이 없다", "부모 구조가 바뀌었다"를 나눠 안내한다.
- **하지 않는 것:** 선택하면 색이 바뀌는지, 어두운 테마 선택을 숨기는지, 다크 모드. 이들은 [later.md](later.md)에 있다.
