# 크롬 확장 개발 가이드라인

블루스카이 웹(`bsky.app`)의 테마 기능을 강화하는 크롬 확장(Manifest V3)을 만들 때의 주의사항과 설계 시 고려사항. 사람과 에이전트 모두 코드를 작성하기 전에 읽는다.

> 상태: 아직 구현 전. 아래 구조와 결정은 초기 방향이며, 실제 구현과 달라지면 이 문서를 같이 고친다.

## 기본 방침

- 런타임/번들러/패키지 매니저는 Bun (자세한 규칙은 루트 [CLAUDE.md](../CLAUDE.md)).
- 확장은 **빌드해서 `dist/`를 로드**하는 방식으로 제공한다. 개발 중에는 `chrome://extensions`에서 "압축해제된 확장 프로그램 로드"로 `dist/`를 가리킨다. 배포 시에는 `dist/`를 zip으로 묶는다.
- Manifest V3는 원격 코드 실행을 금지한다. 모든 코드는 빌드 시점에 번들에 포함해야 하며, CDN 스크립트를 런타임에 불러오지 않는다.

## 권장 구조

```
src/
  content/index.ts      # 콘텐츠 스크립트: 테마 스타일 주입 (iife)
  background/index.ts   # 서비스 워커 (필요할 때만)
  popup/index.html      # 팝업 UI
  popup/popup.ts
  manifest.json
build.ts                # Bun.build + 정적 파일 복사
dist/                   # 빌드 산출물 (git 제외)
```

## 빌드 시 주의할 점

1. **정적 파일은 직접 복사한다.** `bun build`는 JS/CSS/HTML만 처리한다. `manifest.json`, 아이콘 등은 `build.ts`에서 `dist/`로 복사한다. 빌드는 CLI보다 `Bun.build()`를 호출하는 `build.ts`로 통일한다.
2. **출력 파일명을 고정한다.** manifest가 번들 경로를 참조하므로 해시 파일명이 붙으면 깨진다. `naming` 옵션으로 고정하고, HTML 진입점(팝업/옵션)은 번들 후 경로 참조가 맞는지 확인한다.
3. **포맷과 타깃.** 모든 진입점은 `target: "browser"`. 콘텐츠 스크립트는 ES 모듈로 로드되지 않으므로 `format: "iife"`로 낸다. 서비스 워커는 manifest에서 `"type": "module"`을 지정했을 때만 `esm`을 쓴다.
4. **Bun 런타임 API를 확장 코드에 쓰지 않는다.** `Bun.serve`, `bun:sqlite`, `Bun.file` 등은 브라우저에서 동작하지 않는다. 빌드 스크립트(`build.ts`)에서만 쓴다.
5. **개발 중 리로드.** `Bun.serve`의 HMR은 확장 페이지에서 쓸 수 없다. `bun build --watch` 또는 `build.ts`의 watch 모드로 재빌드하고, 확장 새로고침은 `chrome://extensions`에서 하거나 별도 리로드 스크립트를 둔다.
6. **타입.** `@types/chrome`를 설치해 `chrome.*` API 타입을 쓴다.

## 테마 기능 설계 시 고려할 점

- **블루스카이 웹앱의 DOM은 불안정하다.** React Native Web 기반이라 클래스명이 해시되거나 배포마다 바뀔 수 있다. 클래스 선택자에 의존하지 않는다.
- **선택자 우선순위:** `role` 등 시맨틱 속성과 구조 → `<html>` 테마 클래스 → (번역되지 않는 경우에 한해) `aria-label`. 클래스명은 쓰지 않는다. 설정 화면(`/settings/appearance`)을 확인한 결과 색이 CSS 변수가 아니라 요소의 인라인 `rgb(...)`로 지정되어 있어서, 변수 오버라이드가 항상 통하는 것은 아니다. 화면마다 직접 확인한다.
- **`aria-label`은 번역된다.** 사이트 언어에 따라 바뀌므로 선택자로 쓰지 않는다. (예: 색상 모드 `radiogroup`은 라벨이 아니라 "페이지에서 처음 나오는 radiogroup"으로 찾는다.)
- **깜빡임(FOUC) 방지.** 콘텐츠 스크립트는 `run_at: "document_start"`로 두고, `<style>`을 가능한 빨리 주입한다.
- **설정 저장.** `chrome.storage.sync`에 저장한다. 팝업/옵션 페이지에서 바꾸면 콘텐츠 스크립트가 `chrome.storage.onChanged`로 즉시 반영한다. 별도 메시지 패싱은 필요할 때만 쓴다.
- **권한 최소화.** `host_permissions`는 `https://bsky.app/*`로 한정하고, `permissions`는 `storage` 등 꼭 필요한 것만 선언한다.
- **깨짐에 대비한다.** 블루스카이 쪽 변경으로 선택자가 깨질 수 있다. 선택자는 한 곳(상수 모듈)에 모아 두고, 깨졌을 때 고칠 위치가 명확하도록 한다.

## 블루스카이 DOM 메모

직접 확인한 내용만 적는다. (로그인이 필요한 화면은 사용자가 DevTools에서 outerHTML을 복사해 준 것을 바탕으로 한다. 에이전트가 로그인 화면에 직접 접근하지 않는다.)

- **현재 테마:** `<html class="theme--light">`, `<html class="theme--dim">`, `<html class="theme--dark">`(수집 때 `document.documentElement.className`으로 확인)로 표시된다. 시스템 모드일 때도 OS 설정에 따라 이 클래스가 자동으로 바뀐다. 따라서 이 클래스만 보면 "시스템 모드" 분기를 따로 만들 필요가 없다. 바탕은 [selectors.ts](../src/content/selectors.ts)의 `themeBaseOf`로 읽는다.
- **밝은 테마 스타일:** 사용자가 DevTools에서 확인한 값으로, 블루스카이는 `html.theme--light, html.theme--light body, html.theme--light #root { background-color: white; --text: black; --background: white; --backgroundLight: #DCE2EA; }`로 지정한다. 확장의 [theme.css](../src/content/theme.css)는 같은 요소를 더 높은 specificity(`html.theme--light[data-bt-theme]`)로 덮어써서 `!important` 없이 이긴다. 선택이 없을 때(최초 설치 등)는 `data-bt-theme` 속성이 없어 규칙이 걸리지 않으므로 블루스카이 그대로 나온다. 기본값인 "mono"의 팔레트는 블루스카이 원래 색과 같아서 선택해도 겉보기는 같다(어둑함 바탕에서는 검정으로 바뀐다). 알 수 없는 테마 값이어도 배경이 투명해지지 않도록 `var()`마다 블루스카이 원래 색을 대체값으로 둔다.
  - **배경은 인라인 style로도 지정된다:** 대부분의 영역은 요소의 `style="background-color: rgb(255, 255, 255);"`로 칠해져서 위 규칙만으로는 바뀌지 않는다. 그러나 인라인 style은 스타일시트의 `!important`로 덮어쓸 수 있으므로 JS 없이 CSS 주입만으로 해결된다. 요소는 불안정한 원자 클래스(`r-xxxx`) 대신 `[style*="background-color: rgb(255, 255, 255)"]` 속성 선택자로 고른다. 빨간색으로 시험해 적용 범위를 확인했다.
  - **색은 CSS가 아니라 JS 테마 팔레트에서 온다.** 블루스카이의 팔레트(`@bsky.app/alf`의 `createThemes`)가 만든 값을 react-native-web이 인라인 style로 넣는다. 그래서 CSS 파일을 분석해도 색을 알 수 없고, 실제 DOM의 인라인 색을 수집해야 한다. hover는 마우스를 올릴 때 인라인 값이 다른 팔레트 색으로 바뀌는 것으로 보이며(소스에서 직접 확인하지는 못했다), 속성 선택자는 값이 바뀌어도 그대로 걸린다.
  - **밝은 테마에서 수집한 인라인 배경색** (설정, 프로필, 피드 등 여러 화면을 hover하며 수집): `rgb(239,242,246)` 351곳(보조 면), `rgb(249,250,251)` 116곳(hover), `rgb(255,255,255)` 92곳(기본), `rgb(236,72,153)` 분홍, `rgb(0,106,255)` 파랑, `rgb(242,242,242)` 7곳(용도 미확인), `rgba(0,0,0,0.5)` 오버레이, 투명. 처음에는 흰색 계열 세 가지(255 / 249,250,251 / 239,242,246)만 톤다운 대상으로 봤고, 아래 두 번째 수집으로 네 번째(220,226,234)를 추가했다.
  - **밝은 테마를 다시 수집한 결과** (사용자 수집, 2026-10-10): `rgb(249,250,251)` 142곳, `rgb(255,255,255)` 27곳, `rgb(239,242,246)` 17곳, `rgba(0,0,0,0)` 10곳, `rgb(242,242,242)` 6곳, `rgb(220,226,234)` 2곳, `rgb(0,106,255)` 1곳, `rgba(0,0,0,0.75)` 1곳, `rgba(0,0,0,0.5)` 1곳. 첫 수집과 다른 점은 둘이다. (1) **`rgb(220,226,234)`가 새로 나왔다.** 구분선 테두리 색(`border-color`)과 같은 값이고, 어둑함의 `44,58,78`, 어두움의 `35,46,62`와 같은 단계다. 첫 설정 화면 HTML에서 같은 구분선의 테두리가 밝음 `220,226,234`, 어둑함 `44,58,78`이어서 이 대응은 확인됐다. 또 블루스카이가 `html.theme--light`에 지정한 `--backgroundLight: #DCE2EA`와 같은 값(220,226,234)이다. 그래서 theme.css에 네 번째 단계(`-100`)를 밝은 쪽에도 추가했다. `--backgroundLight` 변수 자체는 쓰이는 곳을 몰라서 건드리지 않았다. (2) `rgba(0,0,0,0.75)`가 나왔다. 오버레이라 건드리지 않는다. 그 밖의 곳 수 차이(예: `239,242,246`이 351곳에서 17곳)는 방문한 화면이 달라서이고, 분홍 `236,72,153`이 이번에 안 나온 것도 같은 이유로 보인다. 곳 수는 비교하지 않는다. `242,242,242`는 여전히 용도를 모른다.
  - **어둑함(`theme--dim`)에서 수집한 인라인 배경색** (사용자 수집, 2026-10-10): `rgb(28,39,54)` 61곳, `rgb(21,29,40)` 27곳, `rgb(34,46,63)` 15곳, `rgba(0,0,0,0)` 11곳(투명), `rgb(1,1,1)` 4곳(용도 미확인), `rgb(44,58,78)` 3곳, `rgb(15,115,255)` 1곳(파랑, 주 색), `rgba(0,0,0,0.75)`/`rgba(0,0,0,0.5)` 오버레이. 밝은 테마와 같은 화면의 HTML로 확인된 대응은 기본 배경 `255,255,255` ↔ `21,29,40`, 설정 트랙 `239,242,246` ↔ `34,46,63`이다. hover `249,250,251` ↔ `28,39,54`는 밝기 순서에서 추정한 것이고 hover 때 값이 바뀌는 것을 직접 확인하지는 않았다. `44,58,78`은 구분선 테두리 색과 같은 값이고 밝음의 `220,226,234`와 같은 단계다. 곳 수는 화면마다 달라 밝은 테마와 직접 비교할 수 없다.
  - **어두움(`theme--dark`)에서 수집한 인라인 배경색** (사용자 수집, 2026-10-10): `rgb(0,0,0)` 27곳, `rgb(17,24,34)` 53곳, `rgb(25,34,46)` 41곳, `rgba(0,0,0,0)` 11곳(투명), `rgb(1,1,1)` 4곳(용도 미확인), `rgb(35,46,62)` 3곳, `rgb(0,106,255)` 1곳(파랑, 주 색). 어둑함과 같은 단계로 대응시켰다: 기본 `0,0,0`, hover `17,24,34`, 보조 면 `25,34,46`, 구분선 계열 `35,46,62`. **이 대응은 밝기 순서에서 추정한 것이다.** 어둑함에서는 기본/보조 면만 HTML로 확인했고, 어두움은 HTML을 확인하지 못했다.
  - **어두운 쪽 치환:** 어둑함과 어두움은 바탕마다 원래 색이 다르므로 바탕별로 규칙을 따로 둔다(`html.theme--dim[...]`, `html.theme--dark[...]`). 흑백의 어두운 쪽은 어두움의 원래 색이라 어두움 바탕에서는 그대로이고 어둑함 바탕에서는 검정 계열로 바뀐다. 소프트는 반대로 어둑함 색이다. `rgb(0, 0, 0)` 규칙이 `rgba(0, 0, 0, 0)`(투명)에 걸리지 않는 것은 `rgb(`와 `rgba(`가 달라서다.
  - **"어두운 테마" 선택은 숨긴다:** 어두운 쪽 색을 통합 테마가 정하므로 블루스카이의 어둑함/어두움 선택은 효과가 없다. 이 섹션은 바탕이 밝은 테마여도 색상 모드가 "시스템"이면 렌더링되므로 바탕과 상관없이 찾는다. 우리 섹션 바로 뒤 형제 중 radiogroup이 하나인 것을 `data-bt-hidden`으로 표시하고 theme.css가 `display: none`으로 만든다. (뒤따르는 글꼴 묶음은 radiogroup이 둘이라 걸리지 않는다. 인라인 `style`을 직접 바꾸지 않는 이유는 React가 다시 그릴 때 덮어쓸 수 있어서다.) 화면을 떠나면 속성을 지워 되돌린다. 구조에 의존하는 방식이라 블루스카이가 섹션 구성을 바꾸면 깨질 수 있다.
  - **우리 섹션의 색은 바탕마다 다르다:** 블루스카이의 "색상 모드" 섹션이 바탕별로 쓰는 값(트랙/썸/글자)을 [theme-section.ts](../src/content/theme-section.ts)의 `PALETTES`에 두고, 바탕이 바뀌면 섹션을 새로 만든다. 트랙과 썸은 블루스카이 원래 값 그대로여야 theme.css가 선택한 테마의 색으로 치환한다. 어두움의 트랙(`25,34,46`)과 비선택 글자색(`88,108,137`)은 직접 확인하지 못한 추정값이다.
  - **톤다운 방식:** 원래 색마다 바꿀 색을 [theme.css](../src/content/theme.css)의 `--bt-bg-0/25/50`(어두운 쪽은 `--bt-bg-100`도)에 hex로 직접 적는 단순 치환이다. 흰색을 전부 같은 색으로 바꾸면 hover 색(249,250,251)이 기본 배경보다 밝아져 hover 때 오히려 번쩍이므로, 기본 > hover > 보조 면의 밝기 순서가 유지되게 값을 정한다. (참고: 기본색의 각 채널에 `색조/255`를 곱하면 이 순서가 자연스럽게 유지된다.) 새 색이 필요하면 `--bt-bg-*` 변수와 규칙을 추가한다.
  - **테마 팔레트는 한 곳에서 정한다:** 테마별 색은 theme.css 위쪽의 `--bt-<id>-light-0/25/50`, `--bt-<id>-dark-0/25/50/100`에만 적는다. 작은 원(swatch)도 이 변수를 읽는다. 테마를 추가하려면 [themes.ts](../src/content/themes.ts)의 `THEMES`, [i18n.ts](../src/content/i18n.ts)의 이름, theme.css의 팔레트와 연결 블록을 같이 추가한다. (타입이 i18n 누락을 잡아 준다.)
  - **선택지는 격자로 놓는다:** 한 줄에 3개씩(`COLUMNS`) CSS grid로 놓고, 선택 표시(썸)는 `translate(calc(4px + 열*100%), 행*100%)`로 옮긴다. 썸의 너비와 높이는 `(100% - 8px)`를 열 수와 줄 수로 나눈 비율이다. 모든 칸의 높이가 같다는 전제라서 `translateY`의 100%가 한 줄이다. 테마가 늘면 줄이 늘어난다. 좁은 화면에서는 글자가 말줄임으로 줄어드는데, **폭 360px에서는 이름이 잘린다**(실제 Chrome으로 확인). 한 칸의 글자 공간이 약 48px(원 32px, 간격 8px, 안쪽 여백 16px을 뺀 값)라서 영어 Lavender/Sunset(`Lave…`, `Suns…`), 일본어 イエロー/ラベンダー(`イエ…`, `ラベ…`)가 걸린다. 한국어는 3글자 이하라 들어간다. 해결하려면 좁은 폭에서 원을 글자 위로 쌓거나(theme.css의 미디어 쿼리로 가능) 이름을 줄여야 한다. 아직 하지 않았다.
  - **테마는 현재 여섯 개다:** 흑백, 소프트, 노랑, 숲, 라벤더, 노을. 라벤더와 노을은 사용자가 "임의로" 늘려 달라고 해서 정한 첫 추정값이다.
  - **어두운 쪽 팔레트는 밝은 쪽 색상을 어둡게 해서 만든다:** 노랑, 숲, 라벤더, 노을의 어두운 쪽은 밝은 기본 배경의 색상(hue)을 유지하고 명도만 낮춘 색이다. HSL로 색상은 밝은 기본 배경에서 가져오고(노랑 49°, 숲 107°, 라벤더 251°, 노을 28°), 채도는 테마마다 정했으며(노랑 50%, 숲 30%, 라벤더 38%, 노을 50%), 명도는 -0/-25/-50/-100 단계에서 12%/16%/20%/27%이다. 블루스카이 어둑함(`21,29,40`)이 12%/16%/19%/24% 정도라서 그와 비슷한 밝기로 맞췄다. **노랑의 어두운 쪽은 직접 정한 밝은 겨자색이다:** 노랑은 조금만 어두워져도 노란색이 안 느껴진다는 사용자 판단으로, 어두운 쪽 기본 배경(`--bt-yellow-dark-0`)을 사용자가 `#756520`(명도 약 29%)로 직접 정했다. (`#473e15` → `#e5c63c` → `#c4a92f` → `#927a0f` → `#756520`로 여러 번 바꿨다. 노랑은 어두워지면 금세 색이 안 느껴지고 밝아지면 글자가 안 보이는 사이에서 균형을 찾는 중이다.) 나머지 단계는 같은 색상(49°)과 채도(약 57%)에서 명도만 +3.5%/+7%/+12%(33%/36%/41%)로 올려 `#837124`, `#917d28`, `#a58e2d`로 만들었다(간격은 블루스카이 어둑함의 대략 +4/+7/+12%와 비슷하게 맞췄다. 기본 배경이 밝았을 때의 +5/+10/+18%를 그대로 쓰면 구분선 계열이 너무 밝아진다)(어두운 쪽은 단계가 클수록 밝다는 순서를 유지). 이 값이라서 **블루스카이의 글자색을 바꾸지 않는 한 읽기 어려운 곳이 생긴다.** 선택된 항목과 제목의 흰 글자는 이 배경 위에서 명암비가 기본 배경 5.77, hover 4.82, 트랙 4.06, 구분선 계열 3.23이라 기본 배경과 hover에서는 읽기 좋은 기준(4.5)을 넘는다. 반대로 비선택 글자(`88,108,137`)는 기본 배경 1.08, hover 1.11, 트랙 1.32, 구분선 계열 1.66으로 거의 안 보인다. (이전 값은 `#e5c63c`에서 흰 글자 1.68·비선택 3.18~3.96, `#c4a92f`에서 흰 글자 2.32·비선택 2.31~3.26, `#927a0f`에서 흰 글자 4.19·비선택 1.28~2.33이었다. 배경이 밝을수록 흰 글자가, 어두울수록 비선택 글자가 안 보이는 식으로 한쪽이 좋아지면 다른 쪽이 나빠진다.) **사용자 결정(2026-10-10): 글자색은 바꾸지 않고 그대로 둔다.** 노랑 어두운 쪽에서 비선택 글자가 거의 안 보이는 것은 감수한다. 글자색을 바꾸는 것은 "배경만 바꾼다"는 범위를 넓히는 일이라 하지 않는다. 다시 문제가 되면 노랑의 어두운 쪽에서만 비선택 글자색을 밝게 바꾸는 방법이 있다. (이전에 올렸던 어두운 올리브 `#473e15` 계열에서는 반대로 비선택 글자의 명암비가 1.30이었다. 어둑함 트랙은 2.56, 어두움 트랙은 2.99.) 처음에는 "아주 어두운 노란색" 같은 색을 직접 골랐는데 거의 검정으로 보여서(사용자 피드백) 색이 드러나도록 바꿨다. 흑백(검정)과 소프트(어둑함)는 블루스카이 원래 색이므로 그대로다.
  - **swatch는 지금 바탕의 색 하나만 보여 준다:** 밝은 바탕이면 그 테마의 `--bt-<id>-light-0`, 어둑함/어두움이면 `--bt-<id>-dark-0`이다. 바탕이 바뀌면 섹션을 새로 만들므로 색도 따라 바뀐다. (처음에는 대각선으로 나눠 두 색을 보여 줬으나 색 정보가 많다고 해서 하나로 줄였다.) 색은 `rgb()`가 아니라 `var()`로 칠한다. theme.css는 인라인 `background-color: rgb(...)` 문자열만 찾아 치환하기 때문에 `var()`는 치환되지 않는다.
  - **swatch의 테두리는 `border`가 아니라 안쪽 그림자(`inset box-shadow`)로 그린다:** 흰색이나 검정에 가까운 색이 트랙 위에서 묻히지 않게 하는 얇은 링이다. 예전 두 색 그라데이션에서는 `background-image`가 padding-box 기준으로 반복되어 반투명한 `border` 아래에 반대편 색이 비쳐 가장자리가 깨져 보였다(사용자 화면으로 확인한 증상). 같은 방식을 쓰지 않는 것이 안전하다.
  - **로컬 확인 방법:** 로그인이 필요한 실제 화면 대신, 확인된 구조와 인라인 색으로 만든 가짜 설정 화면에 빌드한 `dist/`를 올려 헤드리스 Chrome(`--headless=new --screenshot`)으로 그려 본다. 밝음/어둑함/어두움과 여러 테마를 한 장에 모아 보면 색 단계, 격자, 숨김 동작을 한눈에 볼 수 있다. 가짜 화면은 실제 DOM의 구조(색상 모드 섹션, 어두운 테마 묶음, 글꼴 묶음이 같은 컨테이너의 형제이고 글꼴 묶음에는 radiogroup이 둘)를 따라야 한다. 이 구조를 어긋나게 만들었다가 숨김이 안 되는 것으로 잘못 보인 적이 있다. 가짜 화면이므로 실제 bsky.app과 다를 수 있어 최종 확인은 사용자 화면이 필요하다.
  - **범위 결정(사용자):** 인라인 값을 치환하는 방식을 유지한다. 처음에는 밝은 테마의 배경만 바꾸기로 했으나, 2026-10-10에 밝음과 어두움을 묶은 통합 테마(흑백, 소프트, 노랑, 숲)로 넓히기로 했다. 어두운 쪽(dim/dark)은 **A 방식으로 정했다(2026-10-10): 어두운 쪽도 확장이 정한 팔레트로 직접 칠한다.** 블루스카이의 "어두운 테마"(어둑함/어두움) 선택과 상관없이 고른 통합 테마가 어두운 색을 정한다(흑백은 항상 검정, 소프트는 항상 어둑함 색). 그래서 블루스카이의 "어두운 테마" 선택은 숨기고, 어둑함과 어두움 두 바탕 각각에서 목표 팔레트로 옮기는 치환표를 둔다. 다른 방식(B: 블루스카이의 어둑함/어두움 선택을 두고 색조만 입힌다)은 "하나의 테마로 통합"한다는 목적에 맞지 않아 택하지 않았다. 지금 적용되는 것은 세 바탕의 배경색이다. 테두리, 글자, 아이콘 채움, 그림자는 하지 않는다. 필요해지면 그 속성의 인라인 값을 따로 수집해 치환표에 추가하는 식으로 넓힌다. (한계: 값의 문자열 형식에 의존하고, 수집하지 못한 색은 바뀌지 않는다.)
  - **저장 키 변경:** 이전 `lightTheme`(comfort/light)은 `theme`(mono/soft/yellow/forest)로 바뀌었고 옮겨 주지 않는다. 확장을 배포하기 전이라 이전 선택은 초기화된다.
  - 같은 이유로 흰색인 다른 요소(예: 설정 화면의 선택 썸)도 함께 바뀐다.
  - `:root`에는 `--rc-*` 변수(`--rc-focus-color: #08f` 등)도 있으나 아직 건드리지 않았다.
- **언어:** 블루스카이 앱의 언어는 `<html lang="ko">`로 확인한다(사용자 확인). 확장의 문구는 브라우저 UI 언어를 따르는 `chrome.i18n`이 아니라 이 값을 기준으로 [i18n.ts](../src/content/i18n.ts)에서 고른다. 지원 언어는 en, ko, ja이고 그 밖의 언어나 값이 없으면 en이다. 일본어(ja)는 사용자 요청으로 추가했다. 번역은 블루스카이 일본어 화면의 용어("カラーモード")에 맞춘 제 최선의 번역이라 원어민 검수를 받지 않았다. `ko-KR` 같은 지역 코드는 앞부분만 본다. 새 문구는 모든 언어에 같이 추가한다. (실제 확인: 값은 `ko`, `en`처럼 지역 코드 없는 형식이고, 앱 안에서 언어를 바꾸면 새로고침 없이 이 속성이 바뀐다. 그래서 `lang` 속성을 관찰하다가 바뀌면 섹션을 다시 그린다. 한국어, 영어, 그때 지원하지 않던 일본어에서 문구가 의도대로 나오는 것도 확인했다. 일본어를 지원한 뒤에는 `lang=ja`로 실제 Chrome에서 그려 확인했다.)
- **이전 화면이 숨겨진 채 남을 수 있다:** 화면을 이동했다가 돌아오면 같은 화면이 DOM에 여러 개 있을 수 있어서, `document.querySelector`로 첫 번째 요소를 고르면 숨겨진 옛 화면을 잡을 수 있다. 요소를 고를 때는 `checkVisibility()`로 보이는 것만 대상으로 한다. (보이는 요소만 고르도록 고친 뒤 "설정 > 모양 → 프로필 → 설정 > 모양" 재진입 시 섹션이 사라지던 증상이 해결되어 확인했다.)
- **SPA:** 라우트 이동 시 페이지가 새로 로드되지 않는다. `MutationObserver`로 화면이 그려지는 시점을 감지한다.
- **설정 > 모양 (`/settings/appearance`):**
  - 섹션 구조: `div > [아이콘+제목 행, div > radiogroup]`. radiogroup은 `[썸, 옵션 래퍼 × N]` 자식을 가진다.
  - 썸은 항상 있지 않다: 새로고침 직후에는 레이아웃 측정 전이라 썸이 없다가 나중에 렌더링된다. radiogroup의 첫 번째 자식이 썸이라고 가정하지 말고, radio를 품지 않은 자식을 썸으로 찾는다.
  - **테마를 바꾸는 중에는 인라인 색이 한꺼번에 갱신되지 않는다.** 다크 → 라이트 전환 중에 트랙과 옵션 글자색은 라이트로 바뀌었는데 제목/아이콘 색은 아직 다크(흰색)인 순간이 있다. 이때 원본을 복제하면 어두운 색이 그대로 박제되어 밝은 배경에서 글자가 안 보인다. 그래서 이 섹션은 원본을 복제하지 않고 [light-theme-section.ts](../src/content/light-theme-section.ts)에서 직접 만든다. 이 섹션은 밝은 테마에서만 보이므로 밝은 테마 팔레트만 가지고 있으면 된다.
  - 선택 상태: `aria-pressed`는 항상 `"false"`라서 쓸 수 없다. 선택은 썸(`translateX`)과 글자색으로만 표현된다. 선택 글자색은 제목 글자색과 같다.
  - 썸의 `width`/`translateX`는 JS가 px로 계산한다. 직접 만든 섹션은 `calc((100% - 8px) / N)`, `translateX(calc(4px + i*100%))`로 비율 계산한다.
  - "색상 모드" 섹션은 항상 있다. "어두운 테마" 섹션은 색상 모드가 "밝음"이면 렌더링되지 않고, "어두움"이면 렌더링되며, **"시스템"이면 OS가 밝아서 지금 바탕이 `theme--light`여도 렌더링된다**(사용자 화면으로 확인). 처음에는 "어두운 테마일 때만 렌더링된다"고 적었는데, 밝은 테마의 HTML을 받은 때가 마침 "밝음"을 고른 상태였던 탓에 생긴 오해다. 컨테이너 자식 순서는 `[색상 모드] [div > 어두운 테마(있을 때)] [div > 구분선 + 글꼴 + 글꼴 크기]`.
  - 색(인라인): 트랙/썸/비선택 글자 — 밝음 `rgb(239,242,246)`/`#fff`/`rgb(135,152,176)`, 어둑함(dim) `rgb(34,46,63)`/`rgb(21,29,40)`/`rgb(88,108,137)`.
- **React 밖의 요소:** 우리가 삽입한 노드는 React가 관리하지 않으므로 리렌더링 때 사라질 수 있다. 관찰자가 계속 확인해서 다시 삽입한다.
- **흰 배경을 `theme.css`가 문자열로 찾는다:** 직접 만든 요소의 흰 배경도 `style` 속성에 `background-color: rgb(255, 255, 255)` 형식(콜론 뒤 공백)으로 써야 `[style*="..."]` 선택자에 걸린다.

## 로컬에서 확인하는 방법

1. `bun run build` (개발 중에는 `bun run dev`로 변경 시 자동 재빌드)
2. `chrome://extensions` → 개발자 모드 → "압축해제된 확장 프로그램을 로드합니다" → `dist/` 선택
3. `https://bsky.app/settings/appearance`에서 밝음 모드로 두고 확인. 코드를 바꾼 뒤에는 확장 새로고침과 페이지 새로고침이 둘 다 필요하다.
